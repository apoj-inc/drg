# DRG infrastructure

## Public example release

This repository is a sanitized example release of infrastructure automation.
It contains no production credentials, private keys, real service endpoints,
or production inventory. Values under `example.test`, the documentation IP
ranges, and `example-org` are placeholders and must be replaced in a private
deployment overlay.

The public release is licensed under Apache License 2.0. See `LICENSE`,
`NOTICE`, and `THIRD-PARTY-NOTICES.md` for licensing information.

Do not add secrets, Terraform state, generated plans, private certificates,
production hostnames, or internal network maps to this repository.

Infrastructure is split into shared resources and independent services.

Run Terraform/OpenTofu from a service directory. Run Ansible from the repository root.

NetBox is the IPAM and dynamic inventory source for service LXC containers. Service Terraform roots register all VM interfaces and IP addresses in NetBox; NetBox-managed addresses are allocated from NetBox prefixes, while legacy/static addresses are recorded for audit and drift detection.

Service Terraform roots use the PostgreSQL `pg` backend. Legacy states that still exist in GitLab managed state can be migrated with the manually triggered `terraform_state_migration` child pipeline. They no longer generate `services/*/ansible/ansible.env`; Ansible reads settings from environment variables through `shared/ansible/inventory/netbox.yml`.

Application variables for the NetBox dynamic inventory live next to it:

- `shared/ansible/inventory/group_vars/all.yml` contains common SSH/Python settings.
- `shared/ansible/inventory/host_vars/*.yml` contains per-service settings.

Those files read values from environment variables and keep local defaults for non-secret settings. GitLab CI/CD and Forgejo Actions pass those values from protected CI secrets.

## CI/CD migration map

Woodpecker is the CI orchestrator, while Dagger executes validation, plans,
and applies in reproducible containers. Forgejo remains the Git host and
pull-request review system. The repository-owned pipeline responsibilities map as
follows:

| GitLab pipeline or component | Forgejo replacement |
| --- | --- |
| `.gitlab-ci.yml` validation jobs | `.woodpecker/validate.yml` |
| `generate-pipeline` | `shared/scripts/generate_woodpecker.py` and `shared/scripts/woodpecker_target.py` |
| `services-pipeline` child pipeline | Woodpecker configuration extension |
| `shared/templates/gitlab-ci-template.yml` | `shared/scripts/run_pipeline.py` and Dagger |
| GitLab Runner / `gitlab_runner_app` | `services/woodpecker_agent` local Dagger agents |
| Forgejo Actions OIDC OpenBao auth | Woodpecker OpenBao secret for deployment credentials |
| Forgejo infrastructure deployment workflow | Woodpecker approval-gated rollout workflows generated by the configuration extension |

Woodpecker runs `shared/scripts/generate_pipeline.py --format
forgejo-manifest` for each matrix service. The generated manifest is not
committed. Pull requests and pushes create one approval-gated pipeline with
matrix workflows for all affected rollout contours read from `platform.yaml`.
Each contour workflow runs plan and apply, and waits for the previous contour,
so the order is A, then B, then C. HA sync, Traefik, and DNS reconciliation
follow the rollout. No Forgejo issue, comment poller, or long-lived Forgejo
API token is used for approval.

Dagger runs the repository commands in a pinned `debian:13-slim` execution
container on a local agent in the target contour. Its cache volume carries the
reviewed `tfplan` from plan to apply.
The Dagger module is in `ci/dagger/src`; it can also be run locally with the
Dagger CLI, for example `dagger -m ci/dagger call validate --source=.`.

### Inspect the effective Woodpecker graph

The generated rollout workflows are created by the configuration extension and
are not committed to the repository. To inspect the effective graph locally,
run:

```sh
python3 shared/scripts/pipeline_graph.py --serve
```

Open `http://127.0.0.1:8765/`. Select the event, branch, changed files, and—
for a deployment—the target in the form `service:cluster:contour`. The viewer
shows workflow dependencies, matrix targets, step dependencies, skipped
contours, and the reason a rollout was not generated. It is read-only and does
not execute Dagger, Terraform, Ansible, or deployment actions.

For a one-shot JSON graph suitable for debugging or other tooling:

```sh
python3 shared/scripts/pipeline_graph.py \
  --event push \
  --branch drunk \
  --changed-file ci/dagger/src/drg_ci/__init__.py
```

### Start an infrastructure deployment

Configure the Woodpecker repository settings as follows:

- enable **Allow pull requests**;
- select **Require approval for -> All events** (`Все события` in the Russian
  UI);
- leave **Allowed users** empty if every pipeline must require confirmation;
- **Allow deployments** is not needed for this automatic flow.

After a push or pull request, Woodpecker creates the validation and rollout
workflows automatically. The pipeline initially shows **Awaiting developer
approval**. An authorized repository operator clicks **Confirm** (`Подтвердить`)
once. The same pipeline then runs validation, applies all affected services in
contour order, and runs Ansible configuration automatically. No **Deploy**
action, target string, or additional pipeline variables are required.

The approval is intentionally before the first step: Woodpecker's native
approval is pipeline-wide, not a step-level gate. Do not select **All pull
requests** if pushes to protected `drunk` must also be protected; use **All
events**. Users listed under **Allowed users** bypass this confirmation, so
only add trusted operators.

Woodpecker Server is deployed hot-hot in contours A and B behind
`ci.example.test`, using the PostgreSQL/Patroni cluster as its shared database.
The server and agents share persistent Forgejo, agent, and gRPC secrets from
OpenBao. `services/woodpecker_agent` deploys one local Dagger agent in each
contour A/B/C; generated workflows select the matching `contour` label. The
Woodpecker control-plane services participate in the application rollout
matrix. The extension is configured through
`WOODPECKER_CONFIG_EXTENSION_ENDPOINT` and
`WOODPECKER_SECRET_EXTENSION_ENDPOINT`. Woodpecker forwards the Forgejo OAuth
netrc credential to the signed extensions, which use it to clone the requested
commit. The secret extension receives no netrc credential and supplies only the
short-lived OpenBao token used by deployment steps.

Forgejo jobs use the `forgejo-host` runner label. These are host runners and
must only execute trusted repository workflows.

The old Forgejo workflow files for Docker utilities and state migration remain
as administrative fallbacks. The automatic
infrastructure CI is no longer defined in `.forgejo/workflows/ci.yml`.

## GitLab CI/CD (coexistence)

Pipelines run automatically on the default branch for changed services. Terraform jobs use one PostgreSQL schema per deployment state:

```text
dockerhub
etcd
openbao
freeipa
keycloak
oauth2_proxy
gitlab
gitlab_runner
forgejo_runner
netbox
network
postgresql
powerdns
redis
traefik
```

The pipeline now has a three-stage process for deployments to ensure manual approval before applying changes:
1. **Plan Stage**: Generates and displays Terraform plans for all affected services
2. **Approve Stage**: Manual approval required (via GitLab UI) before deployment
3. **Deploy Stage**: Applies changes to infrastructure

GitLab CI/CD jobs retrieve secrets from OpenBao using a short-lived GitLab ID
token. Forgejo Actions jobs use Forgejo OIDC tokens. The
secret declarations live in `shared/templates/pipeline-services.yml` (shared
infrastructure credentials) and `services/*/config.yaml` (service credentials).
Terraform receives its declared values as `TF_VAR_*`. Ansible receives only its
native uppercase variable names and never imports `TF_VAR_*`. Its non-secret
`NETBOX_API` value is generated from `environments/example/platform.yaml`.

Before enabling pipelines, initialize and unseal OpenBao, then run the OpenBao
playbook once from a trusted administrator workstation with `OPENBAO_ROOT_TOKEN`
set. This creates the `kv` KV-v2 mount, the GitLab JWT auth mount, the Forgejo
Actions OIDC auth mount, and the `ci` policy/role. Store common values at
`kv/<cluster name>` and service values at the paths declared in each service
config. Do not add the root token or unseal keys to GitLab CI/CD or Forgejo
secrets.

Common required variables:

```text
ANSIBLE_PRIVATE_KEY_FILE
TF_VAR_proxmox_api_token
TF_VAR_root_password
TF_VAR_ssh_public_keys
TF_VAR_netbox_token
TF_VAR_netbox_url
TF_VAR_netbox_validate_certs
```

`ANSIBLE_PRIVATE_KEY_FILE` must be a GitLab CI/CD File variable during
coexistence. Forgejo obtains the same file-valued secret from OpenBao. Scope
the GitLab variable to the deployment environment, for example `Pushkin/*`,
when the same key is shared by all services in that environment.
`TF_VAR_ssh_public_keys` is a Terraform list expression, for example
`["ssh-ed25519 AAAA..."]`; it must contain the public half of
`ANSIBLE_PRIVATE_KEY_FILE`.

The `ANSIBLE_PRIVATE_KEY_FILE` value must be the full multiline unencrypted OpenSSH private key content. Do not store a file path, public key, PuTTY `.ppk`, or a string with escaped `\n` characters.

Some Ansible-only settings can be supplied directly without a `TF_VAR_` prefix when needed, for example `ANSIBLE_USER`, `NETBOX_API`, `NETBOX_VALIDATE_CERTS`, `GITLAB_RUNNER_TOKEN`, and service image tags. Defaults in `shared/ansible/inventory/host_vars/*.yml` cover non-secret values.

Woodpecker provisioning requires these fields in OpenBao at
`kv/services/woodpecker`:

```text
woodpecker_forgejo_secret
woodpecker_agent_secret
woodpecker_grpc_secret
postgresql_woodpecker_password
```

Create a Forgejo OAuth application for Woodpecker with callback URL
`https://ci.example.test/authorize`. Add the resulting client secret to
`woodpecker_forgejo_secret`. The server is installed by the
`services/woodpecker` Ansible playbook and agents by
`services/woodpecker_agent`.

The PostgreSQL switch is intentionally guarded: an existing
`/opt/woodpecker/data/woodpecker.sqlite` must be migrated and moved aside
before the HA server playbook is run. The playbook will not silently start an
empty PostgreSQL-backed Woodpecker instance.

The Woodpecker repository must also have one protected secret:

```text
openbao_deploy_token # short-lived token, supplied only to approval-gated apply workflows
openbao_plan_token   # optional token for non-applying plan workflows
```

The old `forgejo_ci_token` approval secret is no longer used. The native
Woodpecker approval setting controls access to the apply workflows; no Deploy
action or deployment target variable is required.

The Local backend has no isolation and is intended only for this trusted,
private repository. Dagger adds container isolation for pipeline commands, but
the agent still needs Docker access to start the Dagger engine.

Forgejo state migration additionally requires
repository variables `GITLAB_API_URL` and `GITLAB_PROJECT_ID`, plus masked
secrets `GITLAB_TERRAFORM_STATE_USERNAME` and
`GITLAB_TERRAFORM_STATE_PASSWORD`.

## Local Environment

For local Terraform/OpenTofu runs, either export variables with `TF_VAR_*` or put them in a local ignored `proxmox.tfvars` file. For local Ansible runs, export the same variables used by CI, plus `ANSIBLE_PRIVATE_KEY_FILE` pointing at a local SSH key file:

```powershell
$env:NETBOX_API = "http://192.0.2.11:80"
$env:NETBOX_TOKEN = "<netbox-api-token>"
$env:NETBOX_VALIDATE_CERTS = "false"
$env:TF_VAR_netbox_token = $env:NETBOX_TOKEN
$env:TF_VAR_netbox_url = $env:NETBOX_API
$env:ANSIBLE_PRIVATE_KEY_FILE = "~/.ssh/id_ed25519"
```

Terraform roots declare an empty PostgreSQL `pg` backend. CI fills the matching PostgreSQL connection settings automatically. The `TF_HTTP_*` variables below are only needed when reading a legacy GitLab state during migration or for a temporary rollback:

The migration pipeline reads legacy GitLab managed state through `TF_HTTP_*` environment variables and writes the destination through `PG_CONN_STR`, `PGPASSWORD`, and `PG_SCHEMA_NAME`. Normal deployment jobs use PostgreSQL state directly. The GitLab source uses `CI_JOB_TOKEN` by default; if the instance rejects job-token state reads, provide masked/protected `TF_HTTP_USERNAME` and `TF_HTTP_PASSWORD` variables with permission to read Terraform state.

```sh
export SERVICE=gitlab
export TF_HTTP_ADDRESS="https://git.example.com/api/v4/projects/<project-id>/terraform/state/${SERVICE}"
export TF_HTTP_LOCK_ADDRESS="${TF_HTTP_ADDRESS}/lock"
export TF_HTTP_UNLOCK_ADDRESS="${TF_HTTP_ADDRESS}/lock"
export TF_HTTP_USERNAME="<gitlab-username>"
export TF_HTTP_PASSWORD="<personal-access-token>"
export TF_HTTP_LOCK_METHOD="POST"
export TF_HTTP_UNLOCK_METHOD="DELETE"
export TF_HTTP_RETRY_WAIT_MIN="5"
```

### Migrating legacy GitLab state

The root pipeline exposes a manual `terraform_state_migration` trigger. Click
its play button to open a child pipeline with two manual commands:

- `migrate_explicit_states` — enter comma-separated state names. It defaults
  to the DockerHub state.
- `migrate_services` — enter service names and an environment.

Each command provides a `mode` dropdown (`plan` or `apply`) and a boolean
`confirm_apply` control. Enable `confirm_apply` for an apply. DockerHub is the
default target, so the explicit-state command can be started without entering
values. State names and service selections remain comma-separated text fields
because they support multiple arbitrary values.

```text
MIGRATION_STATE_NAMES=production-dockerhub,production-gitlab
MIGRATION_MODE=plan
```

For service selection, the tool derives the same names used by generated
deployment jobs. Non-rollout services use
`<environment>-<service>`. Contour rollouts use
`<environment>-<service>-<cluster>-<contour>`.

After reviewing the non-sensitive migration report, run the job again with:

```text
MIGRATION_SERVICES=dockerhub,gitlab
MIGRATION_ENVIRONMENT=production
MIGRATION_MODE=apply
MIGRATION_CONFIRM=MIGRATE
```

The tool preflights every source and destination, refuses an existing
PostgreSQL destination by default, and leaves the GitLab source unchanged. To
replace an existing destination intentionally, also set
`MIGRATION_ALLOW_OVERWRITE=true`. Do not run Terraform jobs for the selected
states during migration. The source GitLab state remains available for
rollback; restore the old HTTP backend configuration only if a rollback is
required.

Example service-specific local settings:

```powershell
$env:TRAEFIK_ACME_EMAIL = "admin@example.com"
$env:SELECTELV2_ACCOUNT_ID = "<secret>"
$env:SELECTELV2_PROJECT_ID = "<secret>"
$env:SELECTELV2_USERNAME = "<secret>"
$env:SELECTELV2_PASSWORD = "<secret>"
$env:GITLAB_EXTERNAL_URL = "https://git.example.com"
$env:AUTHENTIK_ISSUER_URL = "https://auth.example.com/application/o/gitlab/"
$env:AUTHENTIK_CLIENT_ID = "<secret>"
$env:AUTHENTIK_CLIENT_SECRET = "<secret>"
```

## Initial bootstrap

Bootstrap the platform services that establish NetBox and SDN first. The
clustered PostgreSQL deployment uses the NetBox/service_config flow and should
be deployed after NetBox inventory, DNS, Traefik, and the `prod-app` SDN network
are available.

### 1. Bootstrap NetBox

```sh
cd services/netbox/terraform
tofu init
tofu plan -var-file=proxmox.tfvars
tofu apply -var-file=proxmox.tfvars
```

```sh
ansible-playbook -i 'netbox,' services/netbox/ansible/netbox.yml \
  -e @shared/ansible/inventory/group_vars/all.yml \
  -e @shared/ansible/inventory/host_vars/netbox.yml \
  -e "ansible_host=192.0.2.21"

ansible-playbook -i 'netbox,' services/netbox/ansible/netbox-sdn-bootstrap.yml \
  -e @shared/ansible/inventory/group_vars/all.yml \
  -e @shared/ansible/inventory/host_vars/netbox.yml \
  -e "ansible_host=192.0.2.21" \
  -e netbox_sdn_bootstrap_confirm=true
```

### 2. Reconcile Proxmox SDN from NetBox

After NetBox is running and the SDN objects exist, reconcile Proxmox SDN from NetBox:

```sh
cd services/network/terraform
tofu init
tofu plan -var-file=proxmox.tfvars
tofu apply -var-file=proxmox.tfvars
```

### 3. Deploy etcd and PostgreSQL

After the SDN bridge exists in Proxmox and NetBox inventory is available, deploy
the etcd quorum first, then PostgreSQL:

```powershell
$env:NETBOX_API = "https://netbox.example.test"
$env:NETBOX_TOKEN = "<netbox-api-token>"
$env:NETBOX_VALIDATE_CERTS = "true"
$env:TF_VAR_netbox_token = $env:NETBOX_TOKEN
```

```sh
cd services/etcd/terraform
tofu init
tofu plan
tofu apply

ansible-playbook -i shared/ansible/inventory/netbox.yml \
  services/etcd/ansible/etcd.yml \
  --limit 'etcd-example-cluster-a-*'

cd ../../postgresql/terraform
tofu init
tofu plan
tofu apply

ansible-playbook -i shared/ansible/inventory/netbox.yml \
  services/postgresql/ansible/postgresql.yml \
  --limit 'postgresql-example-cluster-a-*'
```

After Traefik routes and ingress DNS reconcile, applications can use
`postgresql.example.test:5432` for reads and writes. Only the current Patroni
primary accepts application traffic; the other two PostgreSQL instances remain
hot standby failover backups.
